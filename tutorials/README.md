## Conformance notes

- **Standalone carrier (NOTEBOOK_SPEC 2.0 §4):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/zoedepth_metric_depth_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 4-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR3):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD8):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files with `local_files_only=True` and `trust_remote_code=False` through `ZoeDepthForDepthEstimation`/`ZoeDepthImageProcessor` (the BEiT backbone ships in the same SafeTensors file). No pickle checkpoint exists upstream; the notebook's only external dependencies are the pinned PyPI distributions and the Hub at the model revision.
- **Role stages:** `validate_inputs` writes `outputs/zoedepth_metric_depth_input_manifest.json` with the schema (aspect-preserving 384×512 resize, padding, post-processing), the ceilings, the input's observed mode, size and aspect ratio, the flip flag, the verdict, and one recorded rejection finding from the panorama probe; `evaluation_report` writes `outputs/zoedepth_metric_depth_evaluation_report.json` — `not-measurable` on the default path (a drawing has no metres; the probe-depth observations are attached under `observations` and are not a metric), `sample-sanity` with unaligned `abs_rel` and `delta1` and a constant-median-depth baseline only when the learner supplies a metric reference.
- The default sample is a deterministic 640×480 cartoon room drawn in code with Pillow (no text rendering, so its digest is stable across Pillow builds) — the same drawing the smoke run used; it has **no reference depth by design**, so the report is `not-measurable` and the near/far probe ordering (near box 1.69 m before far cabinet 1.87 m in the smoke run) is an observation the learner can check by eye, not a metric.
- Score semantics (UNC1–UNC4): the metres are an estimate with no confidence whose scale follows the model's own indoor/outdoor guess; the notebook says so before the first prediction and again in the interpretation section, and states that a blank image still yields metres (1.43–2.33 m in the smoke run). Flip augmentation is a caller-owned request parameter exposed as a `# @param` value (default `FLIP_AUGMENTATION = False`) and passed explicitly on the `predict` call. The notebook performs no validation of its own — image and flag are checked only by the pipeline's `validate_inputs`/`predict` path.
- Ceilings `MIN_IMAGE_SIDE` (32), `MAX_IMAGE_SIDE` (4096), `MAX_ASPECT_RATIO` (4.0), `DEPTH_KIND`, `DEPTH_UNIT`, `DEPTH_RANGES_M`, `FLIP_AUGMENTATION` and `DELTA_THRESHOLD` (1.25) are printed before the model runs.
- CPU is documented as adequate (card-measured 5.3 s load, 1.5 s per 640×480 image, 2.7 s with flip augmentation; 2.5 s on a 4096×4096 blank image); the notebook states that cost follows the working resolution and that GPU maps need not match CPU maps to the millimetre.
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
